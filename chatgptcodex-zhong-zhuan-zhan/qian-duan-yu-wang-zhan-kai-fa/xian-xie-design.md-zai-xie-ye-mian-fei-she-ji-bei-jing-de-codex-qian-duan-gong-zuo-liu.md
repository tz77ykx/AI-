# 先写 DESIGN.md，再写页面：非设计背景的 Codex 前端工作流

很多人用 Codex 做网站时，会直接输入“帮我做一个有高级感的个人站”。这种要求的问题不在于不够专业，而在于无法检查：什么叫高级感、主要参考是什么、哪些元素不能出现，都没有被写成明确规则。

更稳定的方法是：**先把模糊的审美要求整理成一份设计说明，确认后再写代码。**

本文把这份说明称为 `DESIGN.md`。这是便于项目长期保存和反复使用的文件约定，不是 Codex 强制要求的特殊配置文件；只要 Codex 能够读取，文件也可以使用其他名称。

`DESIGN.md` 不会像 `AGENTS.md` 那样自动成为项目指令。每次开始实现或验收时，都要明确要求 Codex 读取并遵守它。

## 这套方法解决什么问题

它适合没有系统设计背景，但需要完成个人站、作品集、产品介绍页或活动页面的人。目标不是让 Codex 替你“猜一个好看的页面”，而是建立一条可以审阅的工作流：

**明确页面目标 → 选择参考 → 写设计说明 → 人工确认 → 实现页面 → 浏览器检查 → 按需完善素材 → 再次检查 → 局部迭代。**

OpenAI 的前端工作流同样强调：给 Codex 提供截图或设计说明，让它遵守现有项目的设计系统，并在真实浏览器中对照不同屏幕尺寸进行视觉检查。`DESIGN.md` 的作用，就是把其中的“设计说明”保存成可以持续复用的项目文件。

开始前还需要一个能够运行的前端项目，并确保 Codex 可以读取项目文件。这里的“响应式”是指页面会根据桌面端和移动端等不同屏幕调整布局；“设计系统”是项目统一使用的组件、颜色、字体和间距规则。如果 Codex 当前没有浏览器工具，也可以由你手动打开页面、调整窗口尺寸并提供截图。

## 第一步：先明确页面要表达什么

不要先讨论颜色、卡片或动画。先回答这些问题：

* 这是什么页面？
* 主要给谁看？
* 读者看完后应该理解什么？
* 最重要的行动是什么？
* 页面必须包含哪些真实内容？
* 哪些感觉或常见模板特征必须避免？

如果这些问题没有答案，Codex 只能用常见网页模式补空白，最后很容易得到一个结构完整但没有个性的模板页。

可以先让 Codex 帮你整理需求：

```
我准备制作一个 <页面类型>。

先不要写代码，也不要讨论具体技术栈。请通过提问帮我明确：
- 页面要表达什么
- 主要读者是谁
- 最重要的信息和行动是什么
- 必须使用哪些真实内容
- 不希望出现哪些风格和常见模板特征

信息不足时继续提问。最后只输出一份简洁的页面目标说明，等我确认。
```

## 第二步：选择参考，但不要复制参考

参考不是让 Codex 照搬一个网站，而是减少它需要猜测的内容。

选择一个与页面目标、内容类型和主要使用设备接近的参考作为整体方向，再补充少量局部参考。例如：整体布局参考一个站点，字体层级参考另一个页面，动效只参考一个具体交互。每个局部参考只解决一个问题，并且都要说明“学什么”和“不学什么”。

参考分析至少应区分：

* 可以借鉴：视觉层级、留白、字体关系、颜色逻辑、图片处理、组件节奏和交互方式。
* 不应复制：品牌名称、Logo、文案、插图、照片、专有素材以及具有明显识别性的完整页面结构。

有现成截图时，桌面端、移动端和关键交互状态比堆积大量相似截图更有价值。关键交互状态包括菜单展开、按钮悬停、表单错误、空状态等会改变界面的情况。没有截图时，也可以提供网站链接，让 Codex 先分析页面目的、布局、样式规则和响应式变化；如果链接存在登录限制、动态内容无法读取或网络权限不足，就改为提供截图和文字说明。

## 第三步：把目标和参考写成 DESIGN.md

`DESIGN.md` 不需要使用复杂术语，但必须具体到可以检查。建议包含以下内容：

```markdown
# 页面目标

页面类型、目标读者、核心信息、主要行动。

## 内容优先级

必须出现的真实内容，以及从首屏到页尾的信息顺序。

## 参考与边界

主要参考是什么；每个参考借鉴什么；哪些品牌、素材和结构禁止复制。

## 视觉方向

页面气质、颜色角色、字体层级、留白原则、图片处理方式。

## 布局与组件

首屏结构、内容宽度、按钮、导航、卡片、表单和其他关键组件。

## 响应式行为

桌面端与移动端的布局变化、内容折叠和触控要求。

## 动效

哪些地方需要动效、动效解决什么问题、哪些效果不要使用。

## 禁止事项

不新增的颜色、不使用的模板结构、不出现的占位素材和其他边界。

## 验收标准

页面必须完成的功能、需要检查的桌面端和移动端视口、关键交互状态、测试和人工验收项目。
```

让 Codex 生成设计说明时，可以使用下面的指令：

```
根据已经确认的页面目标和参考，创建 DESIGN.md。

要求：
- 使用普通人能理解的表达，但每条规则必须可以执行和检查。
- 明确主要参考、局部参考以及各自只借鉴什么。
- 不复制参考网站的品牌、文案、图片和完整结构。
- 写清页面目标、内容优先级、视觉方向、布局与组件、响应式行为、动效、禁止事项和验收标准。
- 不要把“简洁”“高级”“现代”当作结论，必须解释这些词在本项目中对应的具体设计选择。

写完后先停，不要实现页面。
```

## 第四步：确认设计说明，而不是直接看代码

在 Codex 开始实现之前，先检查 `DESIGN.md`：

* 页面目标是否明确，而不是只写视觉风格；
* 主要参考与局部参考是否分工清楚；
* 颜色、字体、布局和图片是否有具体规则；
* 是否写清移动端怎样变化；
* 动效是否有目的，而不是为了炫技；
* 是否记录了明确的禁止事项；
* 验收标准是否能够在浏览器中检查。

不满意时只修改 `DESIGN.md`。设计规则还没有稳定就开始写页面，会把问题扩散到组件、样式和素材中。

## 第五步：按 DESIGN.md 实现页面

确认设计说明后，再要求 Codex 写代码：

```
先读取已确认的 DESIGN.md，再按照它实现页面。

要求：
- 先阅读项目已有的组件、设计变量（token）、路由和样式约定，优先复用现有系统。
- 不新增 DESIGN.md 之外的主色、字体或主要组件风格。
- 使用真实内容；缺少内容时明确标记，不用无意义的营销文案填充。
- 桌面端和移动端都要适配。
- 不跳过项目已有的测试、类型检查和 git hooks（提交前自动运行的项目检查）。
- 完成后启动项目的本地预览服务，在真实浏览器中检查页面。

最终报告修改文件、测试结果、浏览器检查结果和仍未验证的事项。
```

对于已有项目，“复用现有设计系统”比重新发明按钮、颜色和间距规则更重要。参考图提供视觉目标，项目里的组件和设计变量决定最终如何实现。

## 第六步：在浏览器里对照检查

页面能够编译，不代表视觉结果正确。完成后应在真实浏览器中按照 `DESIGN.md` 写明的视口检查桌面端、移动端和关键交互状态，并把当前页面与参考和 `DESIGN.md` 对照。

不要只说“不好看，重新做”。先指出偏差，再进行局部修改：

```
打开本地页面，先不要修改代码。

请对照 DESIGN.md、参考图和当前页面，列出最影响结果的问题。重点检查：
- 首屏是否准确表达页面目标
- 信息层级与留白是否符合设计说明
- 字体、颜色、按钮和卡片是否偏离规则
- 图片是否像占位素材，裁切和比例是否合适
- 页面是否套用了无关的常见模板结构
- 桌面端和移动端是否存在溢出、遮挡或信息顺序问题

按影响程度排序。确认问题后逐项修改，每次修改后重新截图检查。

保存检查前后的截图，并在最终报告中列出仍未验证或仍与参考存在差异的部分。如果当前没有浏览器自动化工具，请停止自动验收，告诉我需要手动打开哪些页面、使用哪些窗口尺寸、触发哪些交互，并等待我提供截图。
```

浏览器检查的目标不是让 Codex 不断“自由发挥”，而是判断实现是否偏离已经确认的设计说明。

## 第七步：按需要完善图片和素材

图片的用途、比例、位置和视觉约束应在 `DESIGN.md` 阶段确定。已有合适的真实素材时，直接在实现阶段使用；暂时缺少素材时，明确记录缺口，不要让随机图片决定页面方向。

页面的基本版式稳定后，如果视觉结果仍然不理想，再判断是否需要生成或替换素材。页面显得廉价不一定是 CSS 问题，也可能是素材与页面方向不一致；但在换图前，应先确认信息结构、排版和层级没有问题。

需要生成素材时，把用途和约束写清楚：图片放在哪里、承担什么信息、需要什么比例、背景如何处理、是否需要为文字留出空间，以及禁止出现哪些品牌和文字。替换后必须再次在浏览器中检查裁切、清晰度、加载体积和移动端效果。

如果现有素材已经合适，就不要为了“更像 AI 作品”而额外生成图片。

## 常见失败方式

### 只说“做得高级一点”

问题：没有可执行标准，Codex 会回到常见模板。

处理：把抽象形容词翻译成具体规则和禁止事项。

### 只检查能否运行，不检查视觉结果

问题：页面可能没有报错，但层级、间距、响应式和素材仍然偏离目标。

处理：在真实浏览器中对照参考检查，并保留截图作为修改依据。

### 把第三方工具当成必要步骤

问题：工具名称和安装方式会变化，读者容易被配置过程带离主线。

处理：先掌握“目标—参考—设计说明—实现—验证”的方法，再按需要选择工具。

## 可选参考与工具

这些资源可以减少整理设计规则的成本，但都不是完成本教程的前提：

* [Refero Styles](https://styles.refero.design/)：查看面向 AI Agent 的 `DESIGN.md` 示例。
* [web-to-design-md](https://github.com/Paidax01/web-to-design-md)：公开的第三方 Skill 仓库，可从实时网页提取设计证据并生成 `DESIGN.md` 和预览文件；使用前检查其安装要求和授权条件。
* [Taste Skill](https://github.com/Leonxlnx/taste-skill)：第三方前端设计 Skill 集合。Skill 是可以交给 Agent 使用的一组可复用任务说明。截至 2026 年 8 月 23 日，其默认 `design-taste-frontend` 仍标记为实验版本，名称和行为可能继续调整，不能替代项目自己的设计说明和验收标准。

## 最后记住一件事

非设计背景并不意味着只能依赖 Codex 随机生成页面。你真正需要掌握的是：把“我觉得好看”拆成一组能够保存、讨论、实现和检查的设计规则。

**先确认设计说明，再实现；先找到具体偏差，再修改。**
