## 关键发现

* 在既有研究基础上，我们基于对 2025 年 10 月至 2026 年 4 月期间约 400,000 次 Claude Code 会话的[隐私保护分析](https://www.anthropic.com/research/clio)，提出了一个研究交互式智能体编程（agentic coding）的框架。我们评估了任务构成、人机协作方式和成功率。
* 在典型会话中，人主要做出规划决策（做什么），Claude 主要做出执行决策（怎么做）。一个人在会话中展现出的领域专长越深，Claude 每接到一条指示所完成的工作就越多。在编程任务上，平均而言，各主要职业群体取得成功的比率都与软件工程师几乎相同；这里的“成功”是指完成用户设定的目标，并有测试通过或工作已提交等可验证证据。
* 一个人的领域专长越深，会话最终成功的频率就越高，不过中级用户与专家用户之间的差距不大。在我们观察的七个月里，用于调试的会话占比下降了近一半，用途也转向更具端到端特征的智能体式工作：部署和运行代码、分析数据，以及撰写非代码文档。
* 在这七个月里，我们通过与自由职业职位发布信息比较来估算典型任务的价值；这一价值几乎在各类工作中都有上升，平均升幅约为 25%。

## 1. 引言

智能体编程迅速兴起。自 2025 年底以来，有编程智能体参与的 GitHub 项目占比已增长一倍以上，如今 Claude Code 用户平均每周使用该工具 20 小时。没有正规编程经验的人，能否成功指挥智能体完成复杂的技术工作？这些工具的迅速普及和改进，又将对广义上的知识工作产生什么影响？我们目前还无法完整回答这些问题，但可以从 Claude Code 的使用数据中寻找早期信号。

本报告基于对 2025 年 10 月至 2026 年 4 月期间约 235,000 人产生的约 400,000 次交互式会话所做的[隐私保护分析](https://www.anthropic.com/research/clio)，提供 Claude Code 实际使用方式的相关证据。报告延续了我们此前对 [Claude Code 会话自主性指标](https://www.anthropic.com/research/measuring-agent-autonomy)以及 [Claude Code 如何改变 Anthropic 内部工作](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)的研究。在这里，我们提出一个用于描述交互式 AI 编程助手使用情况的框架：所做的是哪类工作、由谁来做，以及工作是否成功。我们关注通过命令行界面（CLI）、[claude.ai](https://claude.ai) 或 Claude Code 桌面应用使用 Claude Code 的情况。通过追踪智能体编程的使用方式如何随着模型能力提升而变化，我们可以更好地理解这些工具会怎样影响编程从业者和知识工作者所处的劳动力市场。

随着智能体逐渐嵌入非编程工作，Claude Code 上正在发生的事情或许预示着知识工作的未来走向。我们发现，Claude 正在处理更复杂、价值也更高的任务。与此同时，智能体编程中仍存在清晰的分工：人决定构建什么，智能体决定如何构建。

我们也观察到，真正提升工具使用效果的是领域专长，而非编程熟练度。具体而言，领域专家取得成功的频率更高，也更容易从错误和误解中恢复。不过，专家与中级用户之间的差距不大。这意味着，只要对某一领域足够熟悉，使用该工具的效果就可以接近那些深度掌握该领域的人。

这些发现让我们得以初步判断劳动力市场可能发生的转变。在我们的数据中，成功取决于一个人对所要解决的问题理解得有多深入，而不是其是否受过编程训练。如果这些模式在整个经济体中同样成立，那么智能体编程工具可能一方面正在承接部分偏重实现的工作，另一方面也让那些真正理解工作中所要解决问题的人获得更多回报。编程智能体并不能替代领域专长——劳动者带给智能体的理解越深入，智能体能够完成的高质量工作就越多。

## 2. 分工

### 2.1 人们用 Claude Code 做什么

为了了解人们使用 Claude Code 做什么，我们将每次会话归入九种工作模式之一，也就是最能描述该会话目标的一项活动。其中四种模式直接涉及编写或维护代码：构建新事物、修复故障、测试代码，以及编排其他智能体或自动化流水线。另有一类是软件运维，包括部署、配置、运行流水线和监控系统。还有两类更侧重于厘清应该做什么：理解现有系统如何运作，以及在实施变更前先做规划。最后两种模式中，采取的行动要么与代码无关，要么代码对最终产品而言只是辅助性手段：分析数据，以及通过演示文稿和其他文字文档进行沟通。

约 56% 的会话用于编写代码（25%）、修复代码（26%），或测试代码及编排智能体和流水线（合计 5%）。软件运维占 17%，规划或探索占 14%，另有 13% 的会话产出分析或文字材料（图 1）。

大多数会话都以现有代码库为基础：48% 主要修改现有代码，另有 17% 探索代码；14% 从头创建新代码。约五分之一的会话完全不涉及代码库。

我们让一个模型读取每次会话的记录并进行分类，随后使用隐私保护分析工具，将分类结果与每次会话都会自动记录的遥测数据进行核对；这些数据包括是否新增或删除了代码行。两种信息来源高度一致。例如，在被分类器标记为创建或修改代码的会话中，超过 90% 都在遥测数据里显示出代码变更。详情参见[附录](https://cdn.sanity.io/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf)。

### 2.2 谁做出哪些决策

Claude Code 的自主程度有多高？能力评测表明，其上限很高，而且仍在上升：在 [METR 时间跨度评测](https://metr.org/time-horizons/)等基准测试中，前沿模型如今已能自主完成原本需要人类耗费数小时的软件任务，并在过程中自行克服障碍。但在现实中，实际使用情况究竟如何？这里，我们考察真实会话在多大程度上由用户或 Claude 主导。

我们从两个角度研究这个问题。首先，我们关注人们在多大程度上将决策交给 Claude；其次，我们考察他们每次交办会让 Claude 执行多少项操作。为了理解一次会话中的决策分工，我们根据会话内容构建了一个隐私保护的决策归属分类器。我们要求分类器列出会话中的所有实质性决策，并将其分为规划决策（做什么、采用何种方案、怎样才算完成）和执行决策（修改哪些文件、编写什么代码、使用何种语言、运行哪些命令）。随后，分类器将每项决策归属于 Claude 或用户，由此为每次会话给出两个数值：用户在规划决策中的占比，以及用户在执行决策中的占比。

#### 图 2：分工

* **副标题：** 人决定做什么，Claude 决定怎么做。
* **图例：** 规划决策；执行决策。
* **横轴：** Claude 在决策中所占比例（%），以 10 个百分点分箱，从 0–10 到 90–100。
* **纵轴：** 会话占比（%）。

_图 2：Claude 在规划决策和执行决策中的占比。图中展示各次会话里，归属于 Claude 而非用户的规划决策（做什么）与执行决策（怎么做）所占比例的分布。在典型会话中，用户做出约 70% 的规划决策，而 Claude 做出约 80% 的执行决策。_

平均而言，人们做出约 70% 的规划决策，但只做出 20% 的执行决策（图 2）。在实际使用中，智能体编程存在清晰的分工：人决定构建什么，智能体决定如何构建。

为了了解会话中的操作委派程度，我们不看会话内容，而是考察其结构。在一次 Claude Code 会话中，用户与 Claude 来回交互：用户给出提示，Claude 采取操作——用户写下一条提示，Claude 随即完成一些工作；接着用户再写一条提示，如此往复。典型会话大约有 4 个这样的轮次。在我们 10 月至次年 4 月的历史数据中，用户每发出一条提示，平均会触发 Claude 执行约 10 项操作，有时甚至超过一百项。在每个轮次中，Claude 会读取文件、编辑代码、运行命令，并平均输出约 2,400 词的内容。

Claude 在两次阶段性确认之间完成多少工作，很大程度上与谁在做决策相对应。当用户掌控执行过程时（即做出超过 80% 的执行决策），Claude 每轮采取的操作较少，约为 8 项。而当 Claude 掌控规划时（即做出超过 80% 的规划决策），其操作数量最高，约为 16 项。

### 2.3 专业程度

Claude 会根据每份会话记录，按照从新手到专家的五级量表，对用户在该任务中表现出的专业程度进行评分。专业程度分类器关注三个信号：用户表述指示时有多精确、用户要求 Claude 验证什么，以及通常是用户纠正 Claude，还是 Claude 纠正用户。需要注意的是，专业程度衡量的内容与职位或一般能力截然不同；更关键的是，它针对具体任务。一位第一次提出 Rust 问题的资深工程师，在 Rust 方面仍是初学者。一位从未使用过 Python 的会计，如果能明确告诉 Claude 某个 Python 脚本必须执行哪些对账规则，并发现脚本在月末结账时处理不当的边界情况，那么这位会计就是该任务的专家。

## 3. 谁在使用 Claude Code，又用它做什么

### 3.1 用户

为了了解是谁在从事这些工作，我们根据会话记录推断每位用户的职业，并将其映射到美国劳工统计局标准职业分类（SOC）体系的 23 个主要职业组之一。分类器被要求只依据以下信号：智能体在会话开始时加载的项目上下文、文件的名称与结构、用户引用的任何资料（如法律文件、临床数据、财务报告、课程大纲等），以及用户使用的词汇。分类器被明确要求，不得将编程这一行为本身视为用户从事编程职业的证据。只有在明确显示软件或数据工作就是用户职业的情况下，会话才会被归入与编程相关的 SOC 类别（计算机与数学职业）。例如，一名律师编写脚本，自动标记某个合同文件夹中缺失的条款；即便该会话的主要工作是编写软件，也会被归入法律职业。如果没有任何信号能够表明用户的职业，该会话就不作分类。

我们能够在约 70% 的会话中推断出用户职业。在这些会话里，涵盖大多数软件相关工作的计算机与数学职业不出意料地成为最大群体。接下来规模较大的依次是商业与金融运营职业，艺术、设计与媒体职业，管理职业，以及生命科学、物理科学与社会科学职业。在我们的样本中，增长最快的非软件职业群体是管理、销售和法律职业。

### 3.2 工作

从 2025 年 10 月到 2026 年 4 月，使用 Claude Code 完成的工作构成发生了显著变化。最明显的变化是，用于修复故障代码的会话占比从 33% 降至 19%（图 4）。取而代之的是，与代码周边环节相关的工作占比提高。软件运维从会话的 14% 增至 21%；写作和数据分析相关会话的占比大致翻了一番，从约 10% 增至 20%。

任务本身的价值也有所提高。我们通过估计一项工作在自由职业市场上的费用来近似每次会话的经济价值，并使用一个包含真实职位发布信息的公开数据集进行校准。按这一指标，从 10 月到次年 4 月，平均每次会话的估计价值上升了 27%。许多工作类型都出现了同样的增长。构建、运维和修复任务的价值都提高了约三分之一或更多，增幅分别约为 43%、34% 和 32%。这些价格估计较为粗略，因此我们主要用它们比较不同时点的不同任务，而不宜把这些估值直接理解为美元金额。关于任务估算器的构建细节，请参见[附录](https://cdn.sanity.io/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf)。

#### 图 4：七个月间工作发生了怎样的变化

* **左图：** 2025 年 10 月至 2026 年 4 月的会话占比（%）。标签：修复和构建工作缩减；非代码工作增长。4 月端点：构建 21%、运维 21%、沟通 20%、修复 19%。
* **右图：** 同期相对 10 月的估计任务价值变化（%）。标签：典型任务的价值提高了。4 月端点：构建 +43%、运维 +34%、修复 +32%、全部 +27%、沟通 +2%。

_图 4：2025 年 10 月至 2026 年 4 月 Claude Code 工作的构成与价值。图中展示七个月内各工作模式的会话占比。用于修复故障代码的会话占比从 33% 降至 19%，而软件运维、数据分析和文档写作的占比有所上升。_

## 4. 成功取决于人自身具备什么

任务的估计价值，是了解 Claude Code 如何帮助人们工作的一个角度。另一个角度，是考察有多少会话取得成功，以及会话的哪些特征与成功相关。在我们采用的所有成功指标中，都能看到一个清晰模式：一个人在会话中展现出的专业程度越高，成功的可能性就越大。大部分提升集中在专业程度量表的低端——新手会话与中级会话之间的差距，大于中级会话与专家会话之间的差距。

在讨论成功会话的特征之前，需要先准确说明我们如何衡量成功。我们无法观察用户在现实世界中的结果，也不能直接询问他们是否通过 Claude 得到了想要的结果。因此，我们采用两项基于会话记录且相互补充的指标。第一项&#x662F;_&#x5224;定成功（judged success）_：一个分类器会读取完整会话记录，判断用户是否成功完成了原本打算做的事情（选项包括：成功、部分成功、失败、无明确目标）。随后，另外两个配套分类器会对支撑这一判断的证据强度进行评分，以确&#x5B9A;_&#x7ECF;验证成功（verified success）_。成功信号分类器会寻找可验证的成功证据，尤其关注与相关工作相匹配的 Git 活动，如提交和拉取请求（PR），以及测试套件通过和用户明确表示认可等情况。它对会话的评分范围从“无信号”，到“弱信号”（1），再到“多个强可验证信号”（5）。与此并行的失败信号分类器，则评估事情出现问题的证据，例如错误、测试失败、反复重试，以及用户对输出提出异议。经验证成功要求会话既被判定为成功，同时还至少存在一个强可验证成功信号。下文分析关注一次会话成功或失败的程度，因此排除了被归为“无明确目标”的会话；这类会话约占完整样本的 7.7%。

### 4.1 专长的回报

那么，哪些类型的会话最成功？事实证明，上文所述的专业程度评分，对会话能否成功影响很大。

一种担忧是，专业程度也许不是真正的驱动因素——专家可能只是选择了不同的任务，或者在其他方面有所不同。在本节中，我们通过以下比较部分回应这一担忧：只比较工作类型、估计价值、发生月份、任务主题和用户所属大类职业均相同的会话，再考察结果如何随用户的专业程度评分而变化。

在我们所有的成功指标上，一个人在会话中展现出的专业程度越高，会话成功的可能性就越大。被评为新手的会话中，达到我们最严格指标——经验证成功——的比例为 15%，达到至少部分成功的比例为 77%。被评为中级或更高级别的会话中，28–33% 达到经验证成功，91–92% 达到至少部分成功（图 5）。

#### 表 2：由分类器得出的成功与失败定义

**至少部分成功**

**定义：** 会话至少部分完成用户的主要目标。

```
outcome = {success, partial success}
```

**转述后的请求：** “为文档网站设置自动部署到 GitHub Pages 的流程，并为每个开放的 PR 创建一个子文件夹。”

**结果：** 工作流已部署并正常运行。会话结束时，链接修复已应用，但尚未确认。任务取得进展，但没有完成。

**判定成功**

**定义：** 会话完成用户的主要目标。

```
outcome = {success}
```

**转述后的请求：** “为将 featured-image 字段与 OpenGraph 图片分离编写一份实施计划。”

**结果：** Claude 起草计划，用户回答“是”，计划文件随后写入，会话结束。没有任何内容被提交或测试。

**经验证成功**

**定义：** 判定成功，并有强可验证的成功证据。

```
outcome = success AND success signal = {4,5}
```

**转述后的请求：** “修正 README 的部署章节——我们现在用 Docker 和 Render，不再用 GitHub Actions。”

**结果：** Claude 编辑文件，用户要求 Claude 提交并推送这些改动。改动已推送至 main 分支。

**判定失败**

**定义：** 会话未完成用户的主要目标。

```
outcome = failure = NOT {success, partial success}
```

**转述后的请求：** “为单样本边界情况添加测试——我们按 TDD 的方式来做。”

**结果：** Claude 提出一个澄清问题；用户没有回答便离开，也没有写入任何内容。没有报错，用户也没有抱怨。

**经验证失败**

**定义：** 判定失败，并有强可验证的失败证据。

```
outcome = failure AND failure signal = {4,5}
```

**转述后的请求：** “把新的搜索端点接入路由器。”

**结果：** 构建因一个未定义的导入项而失败。三次重试都未能修复。用户输入“算了”后离开。

**放弃**

**定义：** 判定失败，且新增代码行数为零。

```
outcome = failure AND lines of code added = 0
```

**转述后的请求：** “每个日期组都只有第一个检查点能加载——其余的只会一直转圈。”

**结果：** 用户在三条消息里又报告了两个错误。Claude 始终没有给出响应。会话结束时写入的代码行数为零。

_表 2：由分类器得出的成功与失败定义。这些示例转述并概括了智能体编程交互公开数据集_ [_SWE-chat_](https://huggingface.co/datasets/SALT-NLP/SWE-chat) _中的真实会话，这些会话由我们的分类器进行了标注。_

在每项指标上，大部分提升都发生在从新手到中级的阶段；从中级到专家，斜率则逐渐减小。我们在[附录](https://cdn.sanity.io/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf)中提供了图 5 背后回归分析的详细信息。类似的梯度也出现在过程中遇到困难的会话里。当失败信号记录到可验证的失败证据时，我们便认为该会话遇到了困难。

#### 图 5：专业程度与会话结局

* **所有会话：** 至少部分成功的比例从新手会话的 77% 升至专家会话的 91%；判定成功从 39% 升至 65%；经验证成功从 15% 升至 33%。
* **遇到困难的会话——仍然成功的比例：** 至少部分成功从 60% 升至 80%；判定成功从 10% 升至 27%；经验证成功从 4% 升至 15%。
* **遇到困难的会话——最终失败的频率：** 图中所示的新手端点分别为判定失败 40%、经验证失败 30%、放弃 19%；专家端点则分别为 20%、18% 和 7%。

_图 5：专业程度与会话结局。会话结果按用户在该任务中的专业程度评分呈现，评分采用从新手到专家的五级量表。左图展示所有会话中被判定为成功或部分成功、被判定为成功，以及达到经验证成功的比例。中图和右图只包括遇到困难的会话（失败信号 ≥ 3），分别展示最终仍符合各种成功定义的比例，以及符合各种失败定义的比例。每个点都是调整后比率——我们只比较工作模式、任务价值区间、月份、任务主题和用户类型（是否从事软件相关职业）均相同的会话，以估计不同专业程度等级之间的差异。关于这些点所依据的回归分析，详见附录。须线表示样本均值的置信区间（其中大部分都小到无法在图中看见）。这些图排除了被成功结果分类器判定为无明确目标的会话。_

这些困难可能表现为错误、测试失败、对同一件事进行多次尝试，或者用户表达沮丧或不满。在遇到困难的会话中，计入上述所有控制因素后，经验证成功的比例从新手会话的 4% 升至专家会话的 15%（图 5）。采用较宽松的指标时，我们发现新手会话至少部分成功的比例为 60%，而中级到专家会话为 80–81%。

我们也追踪了相反方向的关系，即专业程度与各种失败指标之间的关系。需要注意的是，在这项分析中，被判定为失败的会话，是那些连部分成功都没有达到的会话。如果一个遇到困难的会话被判定为失败，且写入的代码行数为零，我们就称其&#x4E3A;_&#x653E;弃_：用户看起来是新手的会话中，有 19% 最终被放弃；其他所有专业程度对应的比例则为 5–7%。换言之，经验最少的用户在难以取得预期结果时，更容易选择放弃。领域专长的部分价值，似乎就在于能够将智能体引向正确方向。

### 4.2 职业的重要性可能低于专业程度

总体来看，软件工程师和其他“计算机与数学职业”从业者约有 30% 的会话达到经验证成功，其他职业的用户则约为 26%。在产出代码的会话中（即新增或修改至少一行代码的会话），这两个数字分别为 34% 和 29%。这 5 个百分点的差距很小；即便两个群体的成功率都在提高，七个月间这一差距也既未扩大，亦未缩小。在产出代码的会话中，我们数据集里规模最大的十种职业，其经验证成功率与软件工程师相比全都相差不超过 7 个百分点。管理类职业的经验证成功率最高，略高于软件工程相关职业。较高的经验证成功率，可能反映了管理技能可以迁移到指挥智能体这一活动上。不过，这一结果也可能部分源自我们的测量方法：验证在一定程度上依赖会话记录中的明确确认，而管理者在得到所需结果时，可能更倾向于通过沟通明确表达。

## 展望

本报告的结果初步呈现出一幅图景：智能体编程放大了某些知识与技能的作用，同时也替代了另一些知识与技能。在生成代码的会话中，各主要职业群体的成功率与软件相关职业群体都只相差几个百分点。编程智能体似乎正在降低编程背景对成功完成编程任务的重要性。

与此同时，成功的会话更有可能体现出领域专长。专业程度评为专家级的会话，其经验证成功率是新手级会话的两倍以上；而当会话遇到困难时，新手放弃会话的比率是其他所有人的数倍。协作方式进一步丰富了这幅图景——领域专家每给出一条指令，都能引导 Claude 完成更多工作。因此，能否引导 Claude 取得成功，更多取决于对某个领域的驾驭，而非编写代码的能力。无论在哪个领域，掌握该领域的人如今都可能完成过去无法胜任的技术工作；而不具备任何此类专长的人，使用同一工具所获得的收益会少得多。此外，收益主要来自胜任，而非精通：只要对领域有切实可用的理解，就能获得大部分收益；在此基础上，深度专精仅会带来少量额外收益。

这些发现仍属初步结论。与我们的大多数研究一样，我们无法衡量现实世界中的结果，例如会话中编写的代码此后究竟会被实际使用还是被丢弃，抑或它是否产出了具有经济价值的成果。此外，本报告排除的非交互式用法占全部活动的相当大一部分。建立一套衡量这类用法的框架，是未来工作的优先事项。我们对会话的所有分类也都取决于模型对会话记录的解读。在[附录](https://cdn.sanity.io/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf)中，我们表明，分类器的结果与独立遥测数据呈现出符合预期的对应关系，并且在大多数会话上与一个性能较强的参考模型判断一致。但要大规模验证分类器仍颇具挑战；Claude Code 会话又增加了一层难度，因为它们可能过长、过于复杂，难以让人工标签充当真值。

随着模型、用户以及二者之间的分工发生变化，本报告所呈现的图景也将不断更新。我们希望，这些指标能帮助我们在重要转变发生之际加以追踪。例如，如果专长的回报随着时间推移开始下降，这可能意味着模型正开始作出目前仍由用户提供的关键判断，也意味着这些工具所带来的收益正从领域专家扩展至更广泛的人群。如果由软件职业之外的用户成功完成的编程会话占比持续增长，则可能表明，软件生产正在成为各领域日常工作的一部分，而不再只是某一单一职业的产物。这些转变将改变谁能从智能体编程中获益、获益多少，并会影响劳动力市场最看重什么。

编程是一个先行案例——随着智能体工具开始承担其他形式的知识工作，软件领域发生的变化很可能预示着未来的发展。
