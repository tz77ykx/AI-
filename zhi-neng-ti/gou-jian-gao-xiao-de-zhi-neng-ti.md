# 构建高效的智能体

发布于 2024 年 12 月 19 日

过去一年里，我们与来自多个行业的数十个团队合作，共同构建基于大语言模型（LLM）的智能体（agents）。一个一致的观察是：最成功的实现方案往往并没有使用复杂的框架或专用库，而是采用了简单、可组合的模式。

在本文中，我们将分享与客户合作以及自身构建智能体过程中的经验，并为开发者提供构建高效智能体的实用建议。

### 什么是智能体？

“智能体”可以有多种定义。一些客户将智能体视为能够在较长时间内独立运行、使用各种工具完成复杂任务的完全自主系统；另一些客户则用这个词来描述遵循预定义工作流的更具规定性的实现。在 Anthropic，我们将所有这些变体都归类为**智能体系统（agentic systems）**，但在**工作流（workflows）** 与 **智能体（agents）** 之间划出了一个重要的架构性区分：

* **工作流（workflows）**：LLM 与工具通过预定义的代码路径进行编排的系统。
* **智能体（agents）**：LLM 动态地指导自身进程与工具使用，并掌控任务完成方式的系统。

下文将详细探讨这两类智能体系统。在附录 1《实践中的智能体》中，我们将介绍两个客户特别从中受益的应用领域。

### 何时使用（以及何时不使用）智能体

在基于 LLM 构建应用时，我们建议先寻找最简单的解决方案，仅在确有必要时才增加复杂度。这意味着有时候根本不需要构建智能体系统。智能体系统通常以延迟和成本为代价来换取更好的任务性能，因此你应当审慎判断这种权衡是否值得。

当确实需要更高复杂度时，工作流为定义明确的任务提供可预测性与一致性；而智能体则更适合在规模上需要灵活性以及由模型驱动决策的场景。然而，对许多应用而言，优化单条 LLM 调用——配合检索（retrieval）与上下文示例（in-context examples）——通常已经足够。

### 何时以及如何使用框架

有许多框架可以让智能体系统的实现变得更简单，包括：

* [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)；
* [AWS 的 Strands Agents SDK](https://strandsagents.com/latest/)；
* [Rivet](https://rivet.ironcladapp.com/)，一个拖放式图形界面 LLM 工作流构建器；以及
* [Vellum](https://www.vellum.ai/)，另一个用于构建和测试复杂工作流的图形界面工具。

这些框架通过简化调用 LLM、定义和解析工具、链式调用等底层标准任务，让入门变得容易。然而，它们往往会增加额外的抽象层，可能掩盖底层的提示（prompts）与响应，使调试变得更加困难。它们也可能诱使你添加不必要的复杂度，而简单方案本已足够。

我们建议开发者从直接使用 LLM API 开始：许多模式只需几行代码即可实现。如果你确实使用框架，请确保理解其底层代码。对底层机制的错误假设是客户出错的常见来源。

请参阅我们的基础工作流 [cookbook](https://platform.claude.com/cookbook/patterns-agents-basic-workflows) 获取一些示例实现。

### 构建模块、工作流与智能体

在本节中，我们将探讨在生产环境中常见的智能体系统模式。我们从最基础的构建模块——增强型大语言模型（augmented LLM）——开始，逐步增加复杂度，从简单的组合式工作流到自主智能体。

#### 构建模块：增强型大语言模型

智能体系统的基本构建模块是一个经过增强的 LLM，这些增强能力包括检索（retrieval）、工具（tools）和记忆（memory）。我们当前的模型能够主动使用这些能力——生成自己的搜索查询、选择合适的工具，并决定保留哪些信息。

![增强型大语言模型](https://www-cdn.anthropic.com/images/4zrzovbb/website/d3083d3f40bb2b6f477901cc9a240738d3dd1371-2401x1000.png)

我们建议重点关注实现中的两个关键方面：根据具体用例定制这些能力，并确保它们为 LLM 提供简单且文档完善的接口。虽然实现这些增强的方式有很多，但一种可行途径是我们最近发布的[模型上下文协议](https://www.anthropic.com/news/model-context-protocol)（Model Context Protocol, MCP），它允许开发者通过简单的[客户端实现](https://modelcontextprotocol.io/tutorials/building-a-client#building-mcp-clients)与日益丰富的第三方工具生态集成。

在本文的剩余部分，我们将假设每一次 LLM 调用都能访问这些增强能力。

#### 工作流：提示链（prompt chaining）

提示链（prompt chaining）将任务分解为一系列步骤，每一步的 LLM 调用都处理前一步的输出。你可以在任何中间步骤添加程序化检查（见下图中的“检查点（gate）”），以确保过程仍在正轨上。

![提示链工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/7418719e3dab222dccb379b8879e1dc08ad34c78-2401x1000.png)

**何时使用这种工作流：** 当任务可以被清晰、干净地分解为固定的子任务时，这种工作流尤为理想。其主要目标是通过让每次 LLM 调用处理更简单的子任务，来用延迟换取更高准确性。

**提示链适用的例子：**

* 先生成营销文案，再将其翻译成另一种语言；
* 先撰写文档大纲，检查大纲是否符合特定标准，再基于大纲撰写文档。

#### 工作流：路由（routing）

路由（routing）对输入进行分类，并将其导向专门化的后续任务。这种工作流实现了关注点分离，并允许构建更专门化的提示。如果没有这种工作流，针对某一类输入的优化可能会损害其他输入上的性能。

![路由工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/5c0c0e9fe4def0b584c04d37849941da55e5e71c-2401x1000.png)

**何时使用这种工作流：** 当复杂任务中存在不同的类别，分别处理效果更好，并且分类可以由 LLM 或更传统的分类模型/算法准确完成时，路由非常有效。

**路由适用的例子：**

* 将不同类型的客户服务查询（一般问题、退款请求、技术支持）导向不同的下游流程、提示和工具；
* 将简单/常见问题路由给更小、成本更低的模型（如 Claude Haiku 4.5），将困难/罕见问题路由给能力更强的模型（如 Claude Sonnet 4.5），以优化整体性能。

#### 工作流：并行化（parallelization）

LLM 有时可以同时处理同一任务，并通过程序化方式聚合输出。这种工作流即**并行化（parallelization）**，它有两种主要变体：

* **分段（sectioning）**：将任务拆分为独立的子任务并行运行；
* **投票（voting）**：多次运行同一任务以获得多样化的输出。

![并行化工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/406bb032ca007fd1624f261af717d70e6ca86286-2401x1000.png)

**何时使用这种工作流：** 当被拆分的子任务可以并行化以加速，或者需要多重视角或尝试来获得更高置信度的结果时，并行化非常有效。对于涉及多个考量的复杂任务，LLM 通常在每次考量都由单独的 LLM 调用处理时表现更好，从而使其能够将注意力集中在每一个具体方面。

**并行化适用的例子：**

* **分段（sectioning）**：
  * 实现护栏（guardrails）：一个模型实例处理用户查询，另一个负责筛查不当内容或请求。这通常比让同一次 LLM 调用同时处理护栏与核心响应效果更好。
  * 自动化评估（evals）以评估 LLM 性能：每一次 LLM 调用评估模型在给定提示上性能的不同方面。
* **投票（voting）**：
  * 审查代码漏洞：多个不同的提示分别审查代码，发现问题时进行标记。
  * 评估某段内容是否不当：多个提示从不同角度评估，或采用不同的投票阈值来平衡假阳性与假阴性。

#### 工作流：协调器-工作者（orchestrator-workers）

在协调器-工作者（orchestrator-workers）工作流中，一个中心 LLM 动态地拆解任务，将其委派给多个工作者 LLM，并综合它们的结果。

![协调器-工作者工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/8985fc683fae4780fb34eab1365ab78c7e51bc8e-2401x1000.png)

**何时使用这种工作流：** 这种工作流非常适合那些无法预先预测所需子任务的复杂任务（例如在编码中，需要修改的文件数量以及每个文件中的修改性质都可能取决于具体任务）。虽然它在拓扑上与并行化相似，但关键区别在于灵活性——子任务不是预定义的，而是由协调器根据具体输入动态决定的。

**协调器-工作者适用的例子：**

* 每次都需要对多个文件进行复杂修改的编码产品；
* 涉及从多个来源收集并分析信息以寻找可能相关信息的搜索任务。

#### 工作流：评估器-优化器（evaluator-optimizer）

在评估器-优化器（evaluator-optimizer）工作流中，一次 LLM 调用生成响应，另一次 LLM 调用在循环中提供评估与反馈。

![评估器-优化器工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/14f51e6406ccb29e695da48b17017e899a6119c7-2401x1000.png)

**何时使用这种工作流：** 当我们有清晰的评估标准，并且迭代式优化能够带来可衡量的价值时，这种工作流尤为有效。两个判断标准是：第一，当人类能够清晰地表达反馈时，LLM 的响应可以明显改进；第二，LLM 本身能够提供这样的反馈。这类似于人类作者在打磨文档时经历的迭代写作过程。

**评估器-优化器适用的例子：**

* 文学翻译：译者 LLM 可能一开始无法捕捉到某些细微差别，但评估器 LLM 可以提供有用的批评意见；
* 复杂搜索任务：需要多轮搜索与分析才能收集全面信息，由评估器决定是否需要进一步搜索。

#### 智能体（agents）

随着 LLM 在关键能力上的成熟——理解复杂输入、进行推理与规划、可靠地使用工具以及从错误中恢复——智能体正在生产环境中逐渐落地。智能体的工作始于人类用户的指令或互动式讨论；一旦任务明确，它们便独立规划与执行，可能在需要进一步信息或判断时返回给人类。在执行过程中，智能体在每一步从环境中获取真实信号（ground truth）（例如工具调用结果或代码执行结果）以评估进展，这一点至关重要。智能体可以在检查点或遇到障碍时暂停以获取人类反馈。任务通常在完成后终止，但也很常见地设置停止条件（例如最大迭代次数）以保持控制。

智能体可以处理复杂任务，但其实现通常很直接。它们通常只是 LLM 在循环中基于环境反馈使用工具。因此，清晰、周到地设计工具集及其文档至关重要。我们将在附录 2《工具的提示工程》中进一步展开工具开发的最佳实践。

![自主智能体](https://www-cdn.anthropic.com/images/4zrzovbb/website/58d9f10c985c4eb5d53798dea315f7bb5ab6249e-2401x1000.png)

**何时使用智能体：** 智能体适用于开放式问题，即难以或无法预测所需步骤数量、也无法硬编码固定路径的场景。LLM 可能会运行多个回合，你必须对其决策有一定程度的信任。智能体的自主性使其非常适合在受信任的环境中扩展任务。

智能体的自主性意味着更高的成本，以及错误累积的潜在风险。我们建议在沙盒环境中进行充分测试，并设置适当的护栏（guardrails）。

**智能体适用的例子：**

以下例子来自我们自己的实现：

* 一个用于解决 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 任务的编码智能体，涉及根据任务描述对多个文件进行编辑；
* 我们的[“计算机使用”（computer use）参考实现](https://github.com/anthropics/anthropic-quickstarts/tree/main/computer-use-demo)，其中 Claude 使用计算机完成任务。

![编码智能体的高层流程](https://www-cdn.anthropic.com/images/4zrzovbb/website/4b9a1f4eb63d5962a6e1746ac26bbc857cf3474f-2400x1666.png)

### 组合与定制这些模式

这些构建模块并非规定性的。它们是开发者可以根据不同用例塑造和组合的常见模式。与任何 LLM 功能一样，成功的关键在于衡量性能并迭代实现。再次强调：你应当只在复杂度能切实改善结果时才考虑增加复杂度。

### 总结

在 LLM 领域取得成功，关键不在于构建最复杂的系统，而在于为你的需求构建合适的系统。从简单的提示开始，通过全面的评估进行优化，只有当更简单的解决方案不足时才引入多步智能体系统。

在实现智能体时，我们努力遵循三项核心原则：

1. 在智能体设计中保持**简洁性**；
2. 通过明确展示智能体的规划步骤来优先保证**透明性**；
3. 通过充分的工具**文档与测试**，精心打造智能体-计算机接口（agent-computer interface, ACI）。

框架可以帮助你快速起步，但在迈向生产环境时，不要犹豫减少抽象层、用基础组件构建。遵循这些原则，你就能打造出既强大又可靠、可维护且受用户信任的智能体。

### 附录 1：实践中的智能体

我们与客户的合作揭示了 AI 智能体的两个特别有前景的应用，它们展示了上述模式的实用价值。这两个应用都说明，智能体在以下任务中价值最大：既需要对话又需要行动、具有明确的成功标准、能够实现反馈循环，并融入有意义的人类监督。

#### A. 客户支持

客户支持将熟悉的聊天机器人界面与工具集成带来的增强能力结合在一起。这对于更开放式的智能体来说是一个自然的契合点，原因如下：

* 支持互动自然地遵循对话流程，同时需要访问外部信息和执行操作；
* 可以集成工具来拉取客户数据、订单历史记录和知识库文章；
* 退款或更新工单等操作可以通过程序化方式处理；以及
* 成功与否可以通过用户定义的问题解决来衡量。

已有几家公司通过按成功解决次数计费的定价模式证明了这种方法的可行性，显示出对其智能体有效性的信心。

#### B. 编码智能体

软件开发领域已展现出 LLM 功能的巨大潜力，其能力从代码补全发展到自主解决问题。智能体尤其有效，原因在于：

* 代码解决方案可以通过自动化测试验证；
* 智能体可以利用测试结果作为反馈来迭代解决方案；
* 问题空间定义明确且结构清晰；
* 输出质量可以客观衡量。

在我们自己的实现中，智能体现在仅凭拉取请求描述就能解决 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准中的真实 GitHub 问题。然而，尽管自动化测试有助于验证功能，人工审查对于确保解决方案符合更广泛的系统需求仍然至关重要。

### 附录 2：工具的提示工程

无论你构建的是哪种智能体系统，工具都很可能成为智能体的重要组成部分。[工具](https://www.anthropic.com/news/tool-use-ga)使 Claude 能够通过在 API 中指定其确切结构与定义来与外部服务和 API 交互。当 Claude 决定调用工具时，它的 API 响应中会包含一个[工具使用块](https://docs.anthropic.com/en/docs/build-with-claude/tool-use#example-api-response-with-a-tool-use-content-block)。工具的定义与规范应当获得与整体提示同等程度的提示工程关注。在本附录中，我们将简要介绍如何对工具进行提示工程。

指定同一操作往往有多种方式。例如，你可以通过编写 diff 或重写整个文件来指定一次文件编辑；对于结构化输出，你可以将代码放在 markdown 中或 JSON 中返回。在软件工程中，这些差异只是表面上的，可以无损地互相转换。然而，某些格式对 LLM 来说写起来要困难得多。编写 diff 需要在新代码写出之前就知道块头中有多少行正在变更；将代码放在 JSON 中（相比 markdown）需要额外转义换行符和引号。

我们在决定工具格式时的建议如下：

* 给模型足够的 token 来“思考”，避免它陷入僵局；
* 让格式尽量接近模型在互联网文本中自然见过的形式；
* 确保没有格式上的“开销”，例如必须准确计算数千行代码的变更数量，或者对写出的代码进行字符串转义。

一个经验法则是：想想在人机交互（human-computer interaction, HCI）上投入了多少精力，然后计划在打造良好的智能体-计算机接口（agent-computer interface, ACI）上投入同样多的精力。以下是一些具体思路：

* 设身处地站在模型的角度。基于描述和参数，这个工具是否显而易见该如何使用，还是需要仔细思考？如果是后者，那么对模型来说很可能也是如此。良好的工具定义通常包括示例用法、边界情况、输入格式要求，以及与其他工具的清晰边界。
* 如何修改参数名称或描述才能让含义更明显？可以把它想象成为你团队中的初级开发者写一份出色的 docstring。当你使用许多相似工具时，这一点尤为重要。
* 测试模型如何使用你的工具：在我们的 [workbench](https://console.anthropic.com/workbench) 中运行大量示例输入，观察模型会犯哪些错误，并迭代改进。
* 采用[防错（Poka-yoke）](https://en.wikipedia.org/wiki/Poka-yoke)理念来设计你的工具，使错误更难发生。

在为我们用于 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 的智能体构建工具时，我们实际上花在优化工具上的时间比整体提示还要多。例如，我们发现当智能体离开根目录后，模型在使用相对路径的工具时会出错。为了解决这个问题，我们将工具改为始终要求绝对文件路径——结果发现模型使用这种方法时几乎不出错。
